Prompt engineering para developers: trucos que no conocías

2026-09-15 · 5 min de lectura · prompt engineering developers IA productividad ejemplos

Introducción

El prompt engineering ha pasado de ser una curiosidad de investigadores a una herramienta esencial para cualquier developer que integra modelos de lenguaje en sus aplicaciones. No basta con lanzar una pregunta genérica; la forma en que estructuramos la solicitud determina la precisión, la velocidad y la utilidad del resultado. En este artículo encontrarás trucos poco conocidos, ejemplos listos para copiar y una guía paso a paso para aplicar estos conceptos en proyectos reales.

Trucos de Prompt Engineering para developers

1. Delimita claramente el contexto y la tarea

Los modelos responden mejor cuando saben dónde empieza y termina la información relevante. Usa delimitadores como --- o ``` para separar el contexto del enunciado.

/* Prompt de ejemplo */
---
Contexto:
You are a senior backend engineer familiar with Node.js and Express.
---
Tarea:
Generate a skeleton for a REST endpoint that receives a JSON payload with fields `name` (string) and `age` (integer) and returns a 201 response.
---

Este formato evita que el modelo mezcle la descripción del rol con la petición concreta.

2. Usa “few‑shot” para guiar el formato de salida

Proporciona ejemplos de la estructura que esperas. El modelo replica el patrón mostrado, reduciendo la necesidad de post‑procesamiento.

/* Prompt con few‑shot */
You are an assistant that returns JSON snippets for code generation.

Ejemplo 1:
Input: Create a Python function that calculates factorial.
Output: {"language":"python","code":"def factorial(n):\n    return 1 if n==0 else n*factorial(n-1)"}

Ejemplo 2:
Input: Write a Bash one‑liner to list all .txt files recursively.
Output: {"language":"bash","code":"find . -type f -name \"*.txt\""}

Ahora genera la respuesta para:
Input: {{user_input}}
Output:

Reemplaza {{user_input}} con la petición del usuario y el modelo producirá JSON listo para consumir.

3. Limita la longitud del output con tokens de control

Indica explícitamente la extensión máxima o el número de ítems que deseas. Esto evita respuestas excesivamente largas que consumen tokens.

/* Prompt con límite de ítems */
Lista hasta 5 mejores prácticas para escribir pruebas unitarias en JavaScript. Cada práctica debe incluir un título y una breve descripción.

El modelo entiende la restricción y genera exactamente cinco elementos.

4. Emplea “role‑play” para obtener respuestas más técnicas

Al asignar un rol especializado (por ejemplo, "senior devops engineer"), el modelo adapta su vocabulario y nivel de detalle.

/* Prompt con role‑play */
Eres un senior DevOps engineer. Explica paso a paso cómo configurar un pipeline CI/CD en GitHub Actions para desplegar una aplicación Docker en AWS ECS.

El resultado suele ser más estructurado y orientado a la implementación.

5. Utiliza “chain‑of‑thought” para razonamiento complejo

Cuando la tarea requiere varios pasos, pide al modelo que explique su razonamiento antes de dar la respuesta final.

/* Prompt chain‑of‑thought */
Quiero optimizar una consulta SQL que une tres tablas y filtra por fecha. Primero, describe brevemente los posibles cuellos de botella y luego propone una versión mejorada de la consulta.

Obtienes tanto el diagnóstico como la solución en un mismo bloque.

6. Incluye instrucciones de formato explícito

Si necesitas Markdown, HTML o JSON, díselo al modelo para evitar conversiones posteriores.

/* Prompt con formato */
Genera un fragmento de Markdown que describa una tabla comparativa entre PostgreSQL y MySQL, con columnas "Características", "PostgreSQL" y "MySQL".

El modelo entrega directamente el Markdown solicitado.

Casos de uso concretos

A continuación, presentamos tres situaciones habituales en las que los developers pueden aplicar estos trucos.

  • Generación de boilerplate: crear rápidamente la estructura de un proyecto en el lenguaje de preferencia.
  • Documentación automática: transformar comentarios de código en documentos Markdown o HTML.
  • Refactorización guiada: pedir al modelo que proponga mejoras específicas manteniendo la lógica original.

Ejemplo práctico: Generar una API REST completa con OpenAI

Supongamos que necesitas una API CRUD en Node.js/Express que maneje recursos tasks. Seguiremos los pasos desde la definición del prompt hasta la validación del código.

Paso 1: Definir el contexto y la petición

---
Contexto:
You are an expert backend developer proficient in Node.js, Express, and MongoDB.
---
Tarea:
Generate a complete Express router for a resource called `tasks`. Include routes for GET /tasks, POST /tasks, GET /tasks/:id, PUT /tasks/:id, DELETE /tasks/:id. Each route must contain basic error handling and use async/await.
---

Ejecutamos el prompt contra la API de OpenAI (modelo gpt‑4‑turbo) y obtenemos el siguiente código:

// router/tasks.js
const express = require('express');
const router = express.Router();
const Task = require('../models/Task');

// GET /tasks
router.get('/', async (req, res) => {
  try {
    const tasks = await Task.find();
    res.json(tasks);
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

// POST /tasks
router.post('/', async (req, res) => {
  try {
    const task = new Task(req.body);
    const saved = await task.save();
    res.status(201).json(saved);
  } catch (err) {
    res.status(400).json({ error: err.message });
  }
});

// GET /tasks/:id
router.get('/:id', async (req, res) => {
  try {
    const task = await Task.findById(req.params.id);
    if (!task) return res.status(404).json({ error: 'Not found' });
    res.json(task);
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

// PUT /tasks/:id
router.put('/:id', async (req, res) => {
  try {
    const updated = await Task.findByIdAndUpdate(req.params.id, req.body, { new: true });
    if (!updated) return res.status(404).json({ error: 'Not found' });
    res.json(updated);
  } catch (err) {
    res.status(400).json({ error: err.message });
  }
});

// DELETE /tasks/:id
router.delete('/:id', async (req, res) => {
  try {
    const deleted = await Task.findByIdAndDelete(req.params.id);
    if (!deleted) return res.status(404).json({ error: 'Not found' });
    res.json({ message: 'Deleted' });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

module.exports = router;

Paso 2: Verificar y ajustar

Antes de copiar el código, revisamos tres criterios:

  • ¿Todas las rutas solicitadas están presentes?
  • ¿Se usan async/await y se captura cada excepción?
  • ¿Los nombres de variables siguen la convención del proyecto?

En este caso, el output cumple con los criterios, por lo que lo añadimos al repositorio.

Checklist accionable

  • ✅ Define claramente el rol y el contexto del modelo.
  • ✅ Usa delimitadores (---, ```) para separar secciones.
  • ✅ Proporciona ejemplos few‑shot cuando necesites un formato estructurado.
  • ✅ Limita la longitud del output si el coste de tokens es una preocupación.
  • ✅ Solicita el formato final (JSON, Markdown, HTML) dentro del prompt.
  • ✅ Valida el código generado con pruebas unitarias o linting.
  • ✅ Revisa que no haya datos sensibles o información confidencial en la respuesta.
  • ✅ Documenta los prompts que funcionaron para reutilizarlos en futuros tickets.

Límites, errores frecuentes y verificación de resultados

Aunque los trucos mejoran la calidad, existen limitaciones inherentes a los modelos de lenguaje:

  • Alucinaciones: el modelo puede inventar nombres de variables o dependencias que no existen.
  • Sesgo de contexto: si el contexto es demasiado amplio, la respuesta puede volverse vaga.
  • Límites de longitud: los prompts demasiado extensos pueden truncarse o generar respuestas incompletas.

Para detectar estos problemas, sigue una rutina de verificación:

// Verificación automática (Node.js)
const { execSync } = require('child_process');
function lintAndTest(file) {
  try { execSync(`eslint ${file}`); console.log('Lint OK'); }
  catch (e) { console.error('Lint errors', e.stdout.toString()); }
  try { execSync(`npm test -- ${file}`); console.log('Tests passed'); }
  catch (e) { console.error('Test failures', e.stdout.toString()); }
}
lintAndTest('router/tasks.js');

Si el lint o los tests fallan, vuelve al prompt y añade una instrucción de "no usar librerías externas" o "mantener la sintaxis ES6".

Recuerda que el modelo no tiene acceso a tu entorno de ejecución; siempre debes validar cualquier código generado antes de desplegarlo en producción.
