Prompt engineering para developers: trucos que no conocías

El prompt engineering se ha convertido en una habilidad esencial para cualquier desarrollador que quiera aprovechar al máximo los modelos de lenguaje grande (LLM). Más allá de preguntar "¿Cómo hago X?", existen estrategias que permiten obtener respuestas más precisas, reutilizables y alineadas con los requisitos de código y arquitectura. En este artículo encontrarás trucos poco divulgados, ejemplos listos para copiar, un caso práctico completo y una checklist accionable.

Trucos esenciales para developers

1. Proporciona contexto estructurado

Los LLM funcionan mejor cuando el contexto está delimitado y sigue un formato predecible. Usa bloques de código, listas o JSON para que el modelo identifique claramente cada pieza de información.

"""Eres un asistente experto en JavaScript.
Objetivo: generar una función que convierta una fecha ISO a formato DD/MM/AAAA.
Restricciones:
- No usar librerías externas.
- Incluir pruebas unitarias con Jest.
Salida: código completo dentro de triple backticks.
"""

Este prompt obliga al modelo a respetar la estructura solicitada y a no mezclar explicaciones con código.

2. Usa "role‑play" para guiar el estilo

Indicar explícitamente el rol y el tono ayuda a que la respuesta sea coherente con la cultura de tu equipo.

"Actúa como senior backend engineer especializado en Go. Explica paso a paso cómo crear un middleware de autenticación JWT, usando comentarios en inglés y siguiendo las convenciones de golint."

El modelo adoptará el vocabulario y las buenas prácticas propias de ese rol.

3. Divide la petición en etapas

En lugar de pedir todo de una vez, solicita primero el diseño y después la implementación. Así reduces el riesgo de que el modelo genere código incompleto o con errores de lógica.

# Etapa 1: diseño
"Describe la arquitectura de una API RESTful para gestionar tareas, incluye endpoints, códigos de estado y diagramas de flujo en texto."

# Etapa 2: implementación
"Con base en el diseño anterior, escribe la implementación en Python usando FastAPI. Incluye ejemplos de request/response."

4. Limita la longitud de salida

Cuando necesitas fragmentos pequeños (por ejemplo, una sola función), especifica un número máximo de líneas o tokens.

"Genera una función en Rust que calcule la factorial de un número entero. Limita la respuesta a 12 líneas de código, sin comentarios adicionales."

5. Incluye pruebas automáticas en la solicitud

Solicitar pruebas unitarias junto con el código mejora la calidad y facilita la integración continua.

"Escribe una clase en Java que represente un árbol binario de búsqueda. Además, genera un archivo JUnit con al menos tres casos de prueba que cubran inserción, búsqueda y eliminación."

6. Emplea ejemplos de “few‑shot” dentro del mismo prompt

Mostrar al modelo ejemplos de entrada‑salida antes de la petición principal le permite inferir el patrón deseado.

"Ejemplo 1:
Input: "Convertir 100 USD a EUR"
Output: "100 USD ≈ 92 EUR"

Ejemplo 2:
Input: "Convertir 250 GBP a JPY"
Output: "250 GBP ≈ 38 500 JPY"

Ahora, convierte: "Convertir 75 CAD a CHF"
"

7. Usa delimitadores claros para separar código y explicación

Los delimitadores como triple backticks o etiquetas <code> evitan que el modelo mezcle ambas partes.

"Genera una consulta SQL que liste los usuarios activos en los últimos 30 días. Devuelve solo el código, encerrado entre triple backticks."

8. Solicita “self‑review” al final

Pedir al modelo que revise su propia salida ayuda a detectar errores comunes.

"Después de generar la función, revisa si hay vulnerabilidades de inyección y sugiere mitigaciones."
Consejo: combinar los trucos 2 y 8 suele producir código que sigue las guías de estilo y, al mismo tiempo, está libre de errores triviales.

Límites, errores frecuentes y verificación de resultados

Los LLM no son perfectos. Entre los límites más habituales se encuentran:

  • Alucinaciones: el modelo puede inventar APIs, paquetes o comportamientos que no existen.
  • Sesgo de datos: las respuestas reflejan los patrones del corpus de entrenamiento, que pueden estar desactualizados.
  • Falta de contexto de proyecto: sin información sobre dependencias o versiones, el código puede ser incompatible.

Errores frecuentes que los developers cometen al usar prompts:

  • No especificar el lenguaje o la versión exacta.
  • Olvidar pedir pruebas o validación.
  • Solicitar demasiado en una sola petición, lo que genera respuestas vagas.

Para comprobar si el resultado mejora, sigue estos pasos:

  1. Ejecuta el código en un entorno aislado (por ejemplo, un contenedor Docker).
  2. Ejecuta pruebas automáticas generadas o escribe las tuyas.
  3. Revisa los logs en busca de advertencias de compilación o runtime.
  4. Compara la salida con casos de uso reales y documenta cualquier desviación.

Caso práctico: generación de código a medida

Supongamos que necesitamos una API en Node.js que reciba una lista de URLs y devuelva el título HTML de cada una. El flujo será:

  1. Diseñar la firma de la función.
  2. Solicitar la implementación con manejo de errores.
  3. Pedir pruebas unitarias con mocha y chai.
  4. Revisar el código generado.

Paso 1 – Prompt de diseño

"Define la interfaz de una función llamada fetchTitles(urls: string[]): Promise<{url:string,title:string}> en TypeScript. La función debe usar fetch, manejar errores HTTP y devolver un array con los títulos. No incluyas implementación todavía."

Respuesta esperada (simplificada):

interface FetchResult {
  url: string;
  title: string;
}

function fetchTitles(urls: string[]): Promise;

Paso 2 – Prompt de implementación

"Implementa la función fetchTitles según la interfaz anterior. Usa node-fetch, limita la concurrencia a 3 peticiones simultáneas y devuelve los títulos dentro de triple backticks. Incluye comentarios breves."

Salida (código dentro de backticks):

```typescript
import fetch from 'node-fetch';
import pLimit from 'p-limit';

interface FetchResult {
  url: string;
  title: string;
}

export async function fetchTitles(urls: string[]): Promise {
  const limit = pLimit(3);
  const tasks = urls.map(url => limit(async () => {
    try {
      const res = await fetch(url);
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      const html = await res.text();
      const match = html.match(/([^<]*)<\/title>/i);
      const title = match ? match[1].trim() : 'Sin título';
      return {url, title};
    } catch (e) {
      return {url, title: `Error: ${e.message}`};
    }
  }));
  return Promise.all(tasks);
}
```

<p><strong>Paso 3 – Prompt de pruebas unitarias</strong></p>
<pre><code>"Genera un archivo de pruebas con mocha y chai para la función fetchTitles. Simula dos URLs: una válida que devuelve un título y otra que provoca un error 404. Usa nock para interceptar las peticiones."
</code></pre>
<p>Salida (código dentro de backticks):</p>
<pre><code>```typescript
import { expect } from 'chai';
import nock from 'nock';
import { fetchTitles } from '../src/fetchTitles';

describe('fetchTitles', () => {
  afterEach(() => nock.cleanAll());

  it('debe devolver títulos correctos', async () => {
    nock('https://example.com')
      .get('/')
      .reply(200, '<html><head><title>Ejemplo');

    const result = await fetchTitles(['https://example.com/']);
    expect(result[0].title).to.equal('Ejemplo');
  });

  it('debe manejar errores HTTP', async () => {
    nock('https://fail.com')
      .get('/')
      .reply(404);

    const result = await fetchTitles(['https://fail.com/']);
    expect(result[0].title).to.match(/^Error:/);
  });
});
```

Una vez ejecutadas las pruebas (npm test), se verifica que el código cumple con los requisitos. Si alguna prueba falla, ajusta el prompt indicando el error específico y vuelve a generar la sección correspondiente.

Checklist accionable

  • ✅ Define claramente el rol y el objetivo del modelo.
  • ✅ Usa contexto estructurado (JSON, listas, bloques de código).
  • ✅ Limita la longitud de la salida cuando necesites fragmentos pequeños.
  • ✅ Solicita pruebas automáticas junto al código.
  • ✅ Pide una revisión o "self‑review" al final del prompt.
  • ✅ Ejecuta el código en un entorno aislado y corre las pruebas.
  • ✅ Documenta cualquier alucinación y corrígela manualmente.
  • ✅ Repite el proceso iterativamente hasta que las pruebas pasen.
